## 阶段 0：环境与安全基线

- 目标：获得可重复的本地开发和安全配置基线。
- 任务：轮换本地启动文件中的疑似凭据；确认 `.env` 配置；建立受支持 Python/依赖版本清单；验证数据/临时目录权限；确认是否仍有第 1-18 章书籍数据，以及 Sakura 与 Provider 测试环境是否可用。
- 依赖：需要人类确认凭据归属、轮换权限和真实 API 测试授权。
- 交付物：无秘密的配置说明、锁定依赖方案、环境检查记录。
- 验收：干净环境可安装依赖；不会把秘密写入 Git；mock runner 完成；书籍数据位置和来源明确；真实端点测试状态明确（成功/未部署/无授权）。

## 阶段 1：流水线契约与质量门禁

- 目标：让现有日译中章节处理可观察、可拒绝不合格结果。
- 任务：定义各阶段输入/输出 schema 和错误处理；统一校验段落映射、引号与输出文件；禁止失败章节自动写入正式 TM；为关键路径补回归测试。
- 依赖：阶段 0 的环境可运行；确定验收样例和可接受的格式差异。
- 交付物：契约文档、自动化测试、质量门禁与失败状态。
- 验收：漏段/多段、错误 schema、引号变化、API 失败等用例可稳定触发明确失败，且不会污染正式输出/TM。

## 阶段 2：书籍知识审核闭环

- 目标：让术语/剧情/风格知识可追溯、可审查、可更正。
- 任务：定义候选与批准数据模型；为术语、概要、人物设定记录来源；建立冲突处理和 TM 发布规则；为抽取脚本增加非破坏性候选输出测试。
- 依赖：阶段 1 的输出/失败契约；需人类确定审核责任和外发数据政策。
- 交付物：知识数据规范、审核流程、迁移/兼容方案、质量测试。
- 验收：错误候选不会自动进入检索；批准项可追溯到源文和审核结论；更正/废弃可回溯。

## 阶段 3：可替换 Provider 与工作流边界

- 目标：解耦日译中流程与模型供应商，保持当前场景行为。
- 任务：定义 Provider 能力接口、超时/重试/限流/错误分类；集中管理模型和响应契约；记录供应商数据政策和成本/质量评估。
- 依赖：阶段 1 契约稳定；阶段 0 确认真实 API 访问条件。
- 交付物：Provider 接口和 mock/contract 测试、端点配置说明。
- 验收：用 mock 或获批的兼容端点替换一个阶段 Provider，不需改动书籍知识格式和流程编排；失败可定位且不丢数据。

## 阶段 4：通用化评估

- 目标：在不损害日轻体验的前提下支持其他语言对和文本类型。
- 任务：抽离语言对、文本类型、分段策略、质量规则、书籍专用上下文等配置；评估不同文本格式和长文本处理；以第二个具体场景验证抽象。
- 依赖：阶段 1-3；明确第二个目标场景、数据集和质量标准。
- 交付物：扩展点定义、迁移说明、第二场景验收记录。
- 验收：新增场景无需复制日轻专用代码；原日译中回归测试继续通过。

## 阶段 5：交互与部署（条件阶段）

- 目标：仅在用户体验和运行需求明确后评估批量任务、交互界面或托管部署。
- 前置调查：确认用户规模、隐私边界、运行预算、任务持久化、部署责任和运维要求。
- 交付物：经人类决策批准的产品/部署方案和运行手册。
- 验收：在明确环境完成备份、恢复、权限、日志脱敏和端到端用户验收。
- 当前状态：仓库未提供 UI、CI、容器或云部署清单；不预选框架或服务，不把该阶段描述为当前可直接实施。

## 状态记录格式

每阶段仅使用 `未开始`、`进行中`、`阻塞`、`完成`。状态更新需记录日期、证据/测试结果、未解决风险和下一步；“代码已写”不等于验收完成。
