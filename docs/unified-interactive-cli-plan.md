## 目标与非目标

### 目标

为现有翻译系统提供一个本地统一入口。用户启动一个脚本后进入持续运行的交互会话，可用方向键浏览并选择功能，也可输入简短 `/...` 命令进入同一功能流程。交互表单负责收集必要信息，避免要求用户记住每个脚本的长参数；业务操作仍由对应工作流负责。

首版应覆盖仓库中已有且可安全接入的主要功能，包括项目/来源、知识、翻译、审阅与发布、TM、EPUB candidate、API 配置和诊断。没有对应实现的功能不得显示为已可用。

### 非目标

- 不替换或删除既有 `scripts/*.py` 命令行入口。
- 不重写翻译、采集、知识治理、审阅或发布业务规则。
- 不增加 Web/桌面/云服务、多用户、并发队列、后台任务服务或远程调度。
- 不创建第二份项目配置系统、凭据存储或持久任务数据库。
- 不绕过 Provider 授权、知识审核、翻译审阅或正式发布门禁。
- 不把 mock 测试结果当作真实 Provider、语义质量或部署验收。

## 建议架构与交互

### 分层

1. **统一启动器**：新增根目录入口 `run_translator.py`。无参数时启动交互会话，`--help` 显示简短用法；启动器只负责初始化界面和分发。
2. **交互会话**：负责主菜单、功能表单、当前会话项目选择、命令提示、确认页面和结果状态。会话内状态仅存内存，退出不写入新历史文件。
3. **命令注册表**：每个功能项描述稳定 ID、中文名称、菜单分类、`/命令` 别名、参数表单、前置检查、操作风险级别及对应适配器。菜单选择与 slash 命令必须调用同一个注册项。
4. **脚本适配器**：通过 `sys.executable`、固定脚本路径和 argv 列表启动现有入口，禁止 `shell=True` 和拼接 shell 字符串。每次只运行一个前台子进程，继承终端输入/输出；启动子进程前暂停交互绘制，完成后恢复。
5. **既有业务层**：所有来源、翻译、知识审核、Provider、TM 与发布约束仍由原脚本和业务模块执行。首版不将其复制到 UI 层。

选择子进程适配的原因：现有脚本包含 `Config` 进程全局状态、独立 argparse 入口及少量 `sys.argv` 临时替换。进程隔离可减少跨任务状态泄漏，并保留旧脚本兼容。若将来需要更细粒度服务 API，另立工作包并用测试证明必要性。

### 运行状态与失败处理

交互状态限定为：`主菜单 -> 功能表单 -> 执行前摘要/确认 -> 运行中 -> 成功/失败/已取消 -> 主菜单`。

- 输入缺失或校验失败：留在表单，说明字段和修正方式，不启动子进程。
- 用户取消：返回上一级或主菜单，状态为已取消，不报告成功或失败。
- 子进程返回非零：显示脚本名称、退出码和经过脱敏的简短错误摘要；保留原脚本自身诊断，不自动重试。
- Ctrl+C：将中断交给当前子进程/工作流处理；恢复终端和菜单状态。不得声称已回滚已经完成的文件写入；可恢复性以现有业务工作流的记录为准。
- TUI 异常或不支持交互终端：提供逐行文本菜单/帮助模式；不在非 TTY 环境强行启用全屏渲染。
- 不做后台并发、跨会话续跑或通用任务状态数据库。长任务的持久状态由现有脚本管理。

## 配置、安全与可访问性

- 用户可在当前会话选择一个项目并复用于后续表单；首版不保存最近项目路径、不扫描或输出项目正文，也不新建项目注册表。
- API 需要既有已保存配置时调用 `configure_api_pool.py` 的加载路径。对临时配置，提供“配置并立即执行”路径，使配置和目标工作流在同一子进程中完成；退出后临时 Key 不在父进程 UI 中保留。
- API Key 继续交给现有隐藏输入和 Windows Credential Manager 机制；TUI 不读取、缓存、回显、记录或加入命令历史。Linux 凭据持久化能力不由 CI 覆盖，不能承诺。
- 每个会触发网络、Provider 请求、知识/译文写入或正式发布的动作，在启动前显示目标项目、输出位置、数据类别、Provider/回退范围以及费用（可计算时；否则标“未知”），明确请求确认。拒绝确认不得调用后端。
- 不改变当前授权默认值或错误处理；不以 UI 确认替代 Provider 的逐类别授权，也不把配置存在解释为端点可用。
- UI 文本和命令参数不写入原文/译文日志；不将子进程完整 transcript 保存到新文件。界面只显示脚本已提供的进度和结果。
- 菜单可全程键盘操作，方向键选择、Enter 确认、Esc 返回；颜色非必需，中文和窄终端有可读降级。提供无全屏的逐行模式，并确保 Ctrl+C 后终端输入回显恢复。

## 实施路线

### 阶段 0：入口盘点与终端依赖验证

- **目标**：确认统一界面的命令契约和平台可行性。
- **任务**：为每个候选脚本记录必需参数、风险/副作用、TTY 需求、已有错误码；验证候选终端库在 Windows/Ubuntu 与 Python 3.14 下的方向键、中文、Ctrl+C、子进程终端交接和恢复。
- **依赖**：本计划文档；不依赖真实 Provider 或项目书籍数据。
- **交付物**：命令注册表草案、支持/不支持动作清单、终端依赖验证记录。
- **验收**：所有拟进入首版的菜单项都有脚本映射、参数来源和操作风险说明；选择的 UI 库通过上述平台验证。先试 `prompt_toolkit`；未通过时再验证 Textual。两者均不通过则停止 UI 依赖接入并记录阻塞，不改用无法满足方向键需求的实现冒充完成。
- **风险与回退**：依赖兼容性或终端差异不明确时，保留现有脚本入口，不开始全功能接入。

### 阶段 1：统一启动器与导航骨架

- **目标**：建立单一启动入口和持续交互会话。
- **任务**：增加 `run_translator.py`、会话状态、主菜单、方向键导航、slash 命令解析、帮助/退出、文本回退；保证菜单项与命令别名共享处理路径。
- **依赖**：阶段 0 通过。
- **交付物**：可运行的交互骨架及命令表。
- **验收**：启动器无参数可进入并持续显示菜单；已注册命令和菜单入口行为一致；未知命令展示帮助；取消或异常可返回主菜单；`--help` 不进入 TUI；现有脚本行为未改。
- **风险与回退**：保留旧脚本独立可用；若全屏模式不可用，回退到逐行模式。

### 阶段 2：表单、项目上下文与只读适配器

- **目标**：让用户可通过交互表单安全选择项目并执行只读操作。
- **任务**：实现会话级项目上下文、字段校验与参数预览；接入依赖/配置诊断、来源清单/版本校验、`--plan-only` 映射预览等只读操作；实现统一子进程启动、退出码和错误展示。
- **依赖**：阶段 1。
- **交付物**：参数表单框架、适配器接口和第一批只读动作。
- **验收**：传给子进程的是 argv 列表而非 shell 字符串；正确处理有空格/Unicode 的路径；未确认的写入动作不会被误分类成只读；测试断言诊断输出不含书籍正文、密钥或完整请求头。
- **风险与回退**：脚本参数无法无歧义生成时，动作保持未接入，不能猜路径或映射。

### 阶段 3：API 配置与来源/知识/翻译动作

- **目标**：通过统一界面执行现有配置和主要工作流。
- **任务**：适配 API 池配置向导、来源采集、知识候选/审核和翻译；在表单中收集项目 URL/目录、目标范围等必需参数；执行前展示权限、授权类别、Provider 和输出影响。
- **依赖**：阶段 2；各业务操作继续依赖其原有门禁。
- **交付物**：配置与核心工作流菜单动作。
- **验收**：密钥使用现有隐藏输入，不进入父 TUI/历史/日志；拒绝授权或最终确认时零子进程启动；“配置并立即执行”能在同一子进程完成配置与目标工作流；缺失知识、配置或授权时保留后端 fail-closed 行为。
- **风险与回退**：不改业务脚本的门禁；适配问题可单项关闭，不影响其他动作。

### 阶段 4：审阅发布、TM/EPUB 与完整验收

- **目标**：覆盖剩余适用脚本并验证完整交互生命周期。
- **任务**：接入审阅/返工/发布、TM 与 EPUB candidate；补齐操作摘要、取消/失败恢复、帮助和用户指南。
- **依赖**：阶段 3。
- **交付物**：首版功能目录、统一 CLI/TUI 用户指南和验收记录。
- **验收**：Windows/Ubuntu Python 3.14 CI 覆盖命令注册/解析、菜单导航、表单、argv、安全退出码、取消和终端恢复；mock E2E 从统一启动器选择一个工作流并返回菜单；Windows 终端人工验收方向键、中文、长任务、取消、错误和再次执行。实际 Provider、语义翻译质量和部署须分开验收。
- **风险与回退**：统一入口故障时继续使用原脚本；新 UI 可以停止发布而不影响已有工作流。

## 测试与发布验收

- **单元测试**：命令别名唯一性、菜单/命令共用路由、命令解析、字段校验、状态转移、确认拒绝、错误分类和脱敏。
- **适配器测试**：`sys.executable`、固定脚本路径、argv、工作目录和环境传递正确；路径含空格/Unicode；非零退出码不丢失；不使用 shell。
- **交互集成测试**：菜单与 slash 命令进入相同动作；成功、取消、参数错误、子进程失败、Ctrl+C 后恢复；配置向导 Key 不进入父进程日志或历史。
- **跨平台测试**：沿用 `.github/workflows/tests.yml` 的 Ubuntu/Windows Python 3.14 矩阵；新增依赖必须能在干净 CI 环境安装。现有 `scripts/run_unit_tests.py` 和 `tests/run_tests.py` 继续运行。
- **人工验收**：至少在目标 Windows 终端验证方向键、中文输入/显示、终端恢复、窄窗口、TUI 暂停并运行子进程，以及重新回到常驻菜单。
- **通过边界**：mock 验证只证明本地路由和脚本边界；不证明真实 API、Provider 计费、内容审核行为、翻译质量或部署就绪。

## 风险与缓解

| 风险 | 影响 | 缓解与失败处理 |
| --- | --- | --- |
| 终端库在目标平台、Python 3.14 或终端仿真器行为不同 | 菜单无法操作或退出后终端状态损坏 | 阶段 0 先做跨平台 spike；提供逐行回退；不通过则保持旧入口并暂停依赖接入。 |
| UI 与后端规则重复实现 | 授权、审核或路径限制出现旁路 | UI 只做输入整理与展示，强制规则继续留在现有业务层；增加拒绝路径回归。 |
| 多脚本全屏/输入冲突 | 密码提示、进度或方向键失效 | 子进程运行前暂停 TUI 绘制并继承终端；API Key 继续由现有隐藏提示收集；逐项测试 Ctrl+C 与恢复。 |
| 子进程部分完成后失败 | 用户误以为操作已回滚 | 保留子进程退出码和业务 run 状态；显示“已失败/可能有部分持久结果”，引导使用对应现有恢复/审计工具，不自动重试。 |
| 误选项目或误触发外发/发布 | 错误目录写入、数据外发或费用 | 项目选择与运行前摘要；高风险动作要求二次确认；拒绝操作默认安全；不默认选择书籍或扩大授权。 |
| 功能入口过多导致首版膨胀 | 延期且难以维护 | 按阶段增量接入；每个动作必须有明确脚本、表单、风险和测试，否则标为未接入。 |
